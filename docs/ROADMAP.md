## 为什么单列一份

前两梯队都是"她现在就能多陪人一点"的东西 ✓。第三梯队每一样要么**依赖外部服务**（TTS）、
要么**要跨端同步**（双端互通）、要么是**另一种使用场景**（番茄钟 / 画中画）——
投入产出比明显低一档，先记账，等真需要了照着做 ✓。

## ⑨ TTS（让她真的"出声"）

- **现状**：她只有文字（气泡 / 流式 ✓），没声音
- **路线**：安卓侧 `TextToSpeech`（系统引擎 ✓，不花钱 ✓）。后端直接回音频那条**不推荐** ✗ ——
  主流聊天 API 基本不回音频，要另接一家，成本和延迟都上去 ✓
- **要做的事**：中文音色；**按整句**读（流式吐出来的是片段，读片段像卡带 ✗）；
  退出 / 静音时立刻停 ✓
- **入口建议**：设置页一个开关，**默认关** ✓（有人觉得她读字吵 ✗）

## ⑩ 番茄钟

- **场景**：她当计时员 —— 开始一句、结束一句 ✓
- **要防的**：进程死了计时没了。**落盘开始时间**，回前台 / 轮询时对账 ✓
  （同提醒事项那套 `_sched` 的思路 ✓，见 `pet_mobile_remind.gd`）
- **交互**：跟她讲「番茄钟 25 分钟」就记下 ✓ —— 时间解析**可以直接复用**提醒事项的
  `_parse_time`（中文数词、时段词它都认 ✓），别另写一份 ✗

## ⑪ 双端记忆互通

- **现状**：安卓端、PC 端各一份 `user://pet_memory.json` ✓，两边的"她"**不共享记忆** ✗
- **难点**（也是为什么先记账的原因）：
  ① 没有账号体系，拿什么认"这是同一个主人"没定 ✗；
  ② 同步走什么通道（网盘 / 自建 / 局域网）没定 ✗；
  ③ 两边都改过的冲突合并策略要设计 ✗
- **前置**：等用户说想要哪种同步方式再动手 ✓

## ⑫ 画中画

- **现状**：安卓 8+ 有 PiP，但 Godot 的模板不直接暴露，要 Java 侧
  `enterPictureInPictureMode()` ✓
- **场景**：看视频 / 玩游戏时把她缩成小窗挂角落 ✓
- **代价**：Activity 生命周期要处理；而且**和悬浮球职责重叠** ✓ ——
  悬浮球本来就是"挂在别的 App 上"的形态，用户大概率已经有球了 ✗
- **结论**：优先级最低的一条 ✓（除非用户明确说"我要在看视频时看到她"）
